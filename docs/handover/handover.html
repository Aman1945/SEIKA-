2   What the audit found

The starting documents claimed 26 modules built and 53 test cases with 34 verified. Checking each claim against the code told a different story.

Claims that did not hold

Documented asWhat the code actually had
“53 test cases, ~34 verified” Zero test files. No test runner in dependencies, no CI. The Python smoke scripts the doc referred to were not in the repository. Every “verified” meant “someone once watched it work”.
Leaderboard hierarchy ✅ built The game scope accepted its parameter and ignored it, because sessions carried no game. A “game board” was the global board renamed. The old test only asserted HTTP 200, so it could not tell.
Auth “Google-ready” A googleId field on two schemas. No OAuth flow, no library.
2FA in the security list A twoFactorEnabled: false boolean. No TOTP anywhere.
Redis, BullMQ, Sentry, PostHog, FCM, Resend, Spaces Redis ran in Docker and the code never connected to it. The rest were comments saying “in P6”. Zero code, zero dependencies.
Cross-zone, Smart Sync, data migration No code at all — and the plan makes cross-zone a sign-off gate and two Smart Sync and two migration cases P0.
“Overall product ~86%” Counted backend logic and treated documentation as a deliverable. Two whole client apps sat inside the “remaining 14%”.

Blockers that would have stopped a launch outright

Nobody could have logged in. OTP had no delivery provider at all — just a TODO(P5) and a development log line. In production the code was generated, hashed, stored, and never sent.
Secrets fell back to public defaults. A deploy missing JWT_ACCESS_SECRET silently used "dev-access-secret", making every token forgeable. The same for the payment webhook secret, which would have let anyone credit any wallet.
No backups. Wallet balances are derived from the ledger and nothing else, so losing that collection loses every customer's balance with no way to reconstruct it. There was no dump, no schedule and no restore procedure.
No version control. git log returned “not a git repository”. No history, no review, no rollback, on software that moves money.

3   How the product works

SEIKA runs a gaming zone: the PCs, the money, the shop, the events, and the player-facing progression that brings people back. One backend holds all the logic; three clients talk to it and decide nothing themselves.

The core loop

Everything else hangs off this sequence, and its most important property is that identity and payment are two separate steps.

1
The PC sits locked, showing a QR code
The kiosk covers the screen. The code is short-lived and refreshes every 40 seconds.
2
The player scans it — and the PC stays locked
Scanning only says who is sitting there. The session is created as PENDING_AUTH with zero XP. This is the product's central rule: a QR scan never unlocks a PC.
3
They choose how long to play, and see the price first
1, 2 or 3 hours as a fixed block, or Open Hour metered per minute with a minimum deposit. The rate is frozen into the session at this moment, so a later price change cannot alter what they were quoted.
4
The Session Authorization Engine decides
Six sources can pay: wallet, cash approved by a cashier, a paid booking, a prepaid package, a voucher, or postpaid where the zone allows it. If none of them passes, the PC stays locked and the player is told exactly what is needed.
5
The server unlocks the PC
Only now, and only from the server. The kiosk obeys; it has no unlock path of its own.
6
They play, and can order to their seat
The shop knows which PC they are at, because the order is bound to their live session. There is no PC number to type and get wrong.
7
The session ends and the PC re-locks
Valid minutes are billed in one database transaction, XP is awarded from those minutes only, level-ups grant coins, and the PC returns to the pool.

The rules the system is built to protect

RuleHow it is enforced
A QR scan is not an unlockAttaching creates a locked session. Unlocking requires a payment source to pass, and the command comes from the server.
XP only from real playXP is computed from valid session minutes. Logging in, scanning, or abandoning a scan earns nothing.
Wallet is money, Coins are notTwo separate ledgers. Coins are never cash-withdrawable and never appear in the money ledger.
Balance is never storedIt is the sum of an append-only ledger. There is no endpoint that writes a balance, and a test asserts that none exists.
Money moves atomicallyEvery debit, refund, booking payment and shop order commits inside a MongoDB transaction or rolls back whole.
Tenants are isolatedOne owner cannot see another's players, wallets, sessions, orders, revenue, staff or audit trail. Co-hosted events share event data only.
Sensitive actions are loggedWho, what role, which zone, old and new values, and a reason where one is required.

The pieces

4   The owner console

Built mobile-first, because the plan makes owner-on-a-phone a P0 case and an owner checks their zone from a phone far more often than from a desk. The sidebar becomes a bottom tab bar under 900px — same routes, same data, same permissions.

The same console on a phone

Not a cut-down version. The plan is explicit that mobile must not be a weaker security layer, so the phone layout runs the same code with the same permissions — only the navigation changes shape.

5   The player app

An installable PWA, designed for someone standing at a PC holding a drink. The two things they came for — their balance, and how to start playing — are above the fold on the first screen.

Where the core rule becomes visible

The hour picker is the moment the product's main rule is made honest to the player. Scanning has already happened and the PC is still locked; the screen says so in plain words, shows the price of every option before it is chosen, and dims anything their balance will not cover. Nothing is charged until they confirm.

The four modules that did not exist

J — Cross-zone events

The plan makes this a sign-off gate: the product cannot be signed off until a cross-zone flow has been tested end to end with two zones and two sets of players. Built: owner-to-owner connections, co-host invitations, per-zone registration where each player pays in their own zone's wallet, per-zone check-in, a shared bracket that exposes event data and nothing private, result verification requiring every zone to submit and agree, a dispute flow that blocks payout, and a prize split that credits each winner in their own zone so money never crosses a tenant boundary.

K — Smart Sync

Two of its cases are P0 and both are about harm: syncing the wrong folder uploads a player's browser cookies, and syncing an anti-cheat folder gets them banned. The policy lives on the server, so it is one auditable decision and testable without a Windows box. The kiosk enumerates candidate files, asks the API to screen them, and reads only what came back allowed. Anti-cheat paths are refused before the whitelist is even consulted, so a mis-configured profile cannot opt a zone in.

N — Data migration

A dependency-free CSV parser, column mapping guessed from common header names, and a validation report that flags bad rows without stopping the good ones. A carried-over balance becomes an OPENING_BALANCE ledger entry, never a stored balance. Imported players are unverified until their first OTP login proves they own the number. The whole import is one transaction.

L7 — Excel and PDF export

Six datasets rendered as CSV, real .xlsx, or a landscape PDF. Values beginning =, +, - or @ are neutralised, because a player picks their own gamer tag and it ends up in a spreadsheet on an owner's machine.

7   Bugs the work found

Eleven real defects, every one in code that had been recorded as verified. Four of them could only be found by running the product rather than reading it.

SeverityDefectWhy it mattered
S1 Two players could be billed on one PC The “one live session per PC” index was keyed on {pcId, status}, making the pair unique — so a PC could hold a pending session and an active one at the same time.
S1 Anyone could cancel a stranger's paid booking The cancel path took an actor id and never checked it. Any signed-in player could free someone else's reserved seat by id, across zones.
S1 Anyone could trigger a debit on another player's wallet Paying a booking debited the booking's player, and the same missing check let a stranger start it.
S1 A player in zone A could order from zone B The order took zoneId from the request body. The seat is now derived from the player's live session, so it is impossible by construction.
S2 The game leaderboard was the global board renamed scope=game was accepted and ignored. The existing test asserted only HTTP 200, which a board with the wrong contents passes.
S2 Migration uploads could never have worked The endpoint documented 5 MB while the body parser ran at its 100 KB default, and an oversized body returned 500 instead of 413.
S2 Order lines showed ₹NaN The queue converted the order total from Decimal128 but not the per-line prices, so any client computing price × quantity got NaN. Visible on the first order that reached the queue.
S2 The SDK could not call the API from a browser fetch was stored detached from window, throwing “Illegal invocation”. Nothing but a real browser would have caught it.
S2 The player app could not reach the API CORS allowed only port 3000; the player app runs on 3001.
S2 Concurrent payment callbacks could double-credit Idempotency was a read-then-write. Two simultaneous deliveries both passed the check. Now a conditional claim inside the transaction, tested with three at once.
S2 Player profile customization did not exist Plan case A6. The endpoint was simply absent.
One test-design lesson worth keeping. The old suite had a case for the game leaderboard, and it passed for months while the feature was absent, because it only checked that the response was HTTP 200. A test that asserts a status code and not a result can pass on a feature that was never built.

8   Testing

167 automated cases, mapped one-to-one onto the plan's modules, running in CI on every push. They replace 53 manual ones that had no reproducible form.

How they run

The API suite spins up its own in-memory MongoDB replica set — not a standalone — so every money path executes inside a real multi-document transaction. Testing a wallet against a standalone mongod silently skips the thing most worth testing. No Docker, no seeding, no manual steps.

What they actually assert

AreaExamples
MoneyBalance equals the sum of the ledger. No endpoint can write a balance. A webhook replay credits once. A forged signature credits nothing. A failure between debit and commit leaves no partial write. A refund reverses wallet, XP and coins together.
The core ruleA QR scan leaves the PC locked with zero XP. An insufficient balance never unlocks. Cash needs a cashier. A one-use voucher is exhausted after one use. A package deducts minutes and leaves the wallet alone.
IsolationOwner A cannot see owner B's sessions, orders, products, analytics, audit trail or wallets. Staff of one zone cannot act on another's bookings. A co-host sees shared event data and never private customer or financial data.
Hour selectionA 2-hour block freezes its price and bills the block even when ended early. Open Hour needs a deposit and meters actual minutes. Anything that is not 1, 2 or 3 hours is refused.
Cross-zoneThe full two-zone flow the plan requires: connect, co-host, register and check in per zone, agree on results, dispute, resolve, settle — with prizes credited in each winner's own zone.
Smart SyncBrowser profiles, chat clients, credential stores, personal folders, executables, traversal and absolute paths all refused; anti-cheat paths refused even when a profile wrongly allows them, and logged.
OperationsReadiness returns 503 when Mongo is unreachable. Crash reports carry no OTPs, tokens, client keys or player data. Rate limiting degrades rather than failing the API.

What is not automated, and why

  • The two client UIs. Both were driven end to end by hand in a browser — sign in, attach, choose a block, play, order to seat, top up — and the wallet arithmetic checked against its ledger. Automated UI tests are not written yet.
  • Kiosk behaviour on Windows. The disk-side Smart Sync logic has 10 tests that run without Electron, but the lock itself needs real hardware.
  • Load. A 40-PC zone all heartbeating and ordering has not been simulated.

9   Running it in production

Backups — the part that mattered most

Wallet balances are derived from the ledger and nothing else. Losing that collection is not losing analytics; it is losing every customer's balance with no way to reconstruct it. There were no backups at all.

PieceWhat it does, and why that shape
Dump, every 4 hoursmongodump --oplog, so the dump is point-in-time consistent across collections and a restored ledger is trustworthy rather than approximately right.
Verify before trustingEvery dump is opened with --dryRun. A suspiciously small dump fails the job instead of replacing a good one.
Encrypt and move off-boxGPG, then upload. A backup on the same droplet does not survive the droplet.
Dead-man's switchA ping on success. Without it, “no alert” and “no backups for three weeks” look identical.
Monthly restore drillRestores into a throwaway database and asserts the collections exist, every balance is computable and non-negative, no ledger row is orphaned, and the session-guard index came back — that last one is a correctness check, since without it two players can be billed on one PC.

Refusing to start unsafely

A production deploy now fails loudly rather than running insecurely. It will not boot with development JWT or webhook secrets, without an OTP provider that can actually deliver, with payments in mock mode, with a localhost database URI, or with localhost left in the CORS list. Each of those fails silently and expensively otherwise.

The rest of the stack

Monitoring
/health for liveness; /health/ready pings Mongo for real and returns 503 when it cannot serve — a socket can be “connected” to a primary that no longer accepts writes. Sentry reports crashes with OTPs, tokens and player data scrubbed out.
Rate limiting
Backed by Redis so the window is shared across instances; an in-process counter gives an attacker the full quota per instance behind a load balancer. It degrades to local counting rather than taking the API down with it.
TLS & proxy
Nginx with HSTS, and a 7-day read timeout on the Socket.IO path so kiosks do not reconnect every minute. The payment webhook is deliberately exempt from coarse rate limits: dropping it loses a top-up the player has already been charged for.
Deploy
Takes a backup, builds, waits for readiness, swaps, and rolls itself back if the new release never becomes ready. The outgoing image stays tagged, so a rollback is one command and not a rebuild.
CI
Typechecks every package, runs both test suites, builds both clients and the production image, on every push.

10   What remains

PriWorkEstimateWhy
1 Run the kiosk on real Windows ~1 week Never done. Plan §11 forbids signing this off by simulation. Needs two PCs, Assigned Access configured, and a full day of lock, unlock, heartbeat and Smart Sync.
2 Restore drill against a production-sized dump 1 day The tooling exists and passes on test data. Timing it on real volume turns the recovery window into a number instead of a hope.
3 Remaining client screens 1–2 weeks Bookings and rewards in the player app; announcements and booking management in the console.
4 Load test a 40-PC zone 2–3 days Heartbeats, live sessions and the order queue under real concurrency.
5Multi-node MongoDB2–3 days The single node gives transactions, not high availability.
6Google OAuth, 2FA, no-show automation1 week Listed in the original plan, never built. None of them blocks a pilot.
7Pilot zone2 weeks min. One real zone with real PCs, a cash counter and real network drops, gated on zero open S0/S1 issues.
Recommended order. Windows first — it is the only item that can invalidate an assumption rather than just take time. The restore drill next, because it is a day and it retires the largest financial risk. Then the remaining screens, which can run in parallel with pilot preparation.

Practices worth keeping

  • The test suite is the release gate. A plan case with no automated test is not verified; it is something someone once saw work.
  • Assert results, not status codes. A test that only checks HTTP 200 can pass on a feature that does not exist.
  • Check money against the ledger, never through a response body.
  • Give tenant isolation a test per feature, not one test in total.
  • Run the thing. Four of the eleven defects surfaced only in a real browser, and one of them would have shipped.

11   How to run it

Everything, locally

pnpm install
pnpm dev:api:mem    # API + in-memory Mongo replica set → :4000
pnpm dev:dashboard  # owner console → :3000
pnpm dev:player     # player app → :3001

No Docker needed: the API starts its own in-memory replica set, so transactions work out of the box.

A zone to click around

POST /api/dev/seed creates a zone, a PC, and one staff member per role.

  • Staff sign in with 9700000001–04 (cashier, manager, technician, event manager).
  • Any phone number creates a player.
  • Outside production the API returns the OTP in its response, so both apps autofill it.

Tests

pnpm test          # 157 API + 10 kiosk
pnpm typecheck    # every package

Roughly 20 seconds for the whole suite.

Production

infra/README.md covers the full path: Docker Compose for Mongo and Redis, nginx with certbot, the backup cron and the monthly restore drill, and the deploy script.

The API refuses to boot on an unsafe production configuration, and tells you which setting is wrong.
